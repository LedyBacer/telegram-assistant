assumption, the date it was made, and the reason.

| 10 | API auth for Mini App endpoints is initData-derived (verified `user.id`) with no bearer tokens. | 2026-09-21 | SPEC describes Telegram initData HMAC validation as the Mini App auth mechanism. |
| 11 | Manual task drafts accept an optional `remind:` line with comma-separated integer offsets in minutes before the item's start time (0 = at start, negative = after start). Reminders are item-linked durable jobs. | 2026-09-22 | SPEC §8 requires item-linked reminders with one or more offsets, but the draft grammar is unspecified; a single optional line keeps the manual format simple and matches the AI-draft fields to be added in M7. |
| 12 | In the task-creation flow, the manual line format is tried first and the AI (structured `AITaskDraft`) is used only when manual parsing fails; AI output is kept in typed FSM state and rendered as a preview before confirmation. | 2026-09-22 | SPEC §6 requires AI-structured drafts with human confirmation, but the manual format is a deterministic, credential-free path (SPEC §30: tests must not need real keys). | 13 | Structured AI output sends **no** `response_format` (llama.cpp rejects/ignores the OpenAI-only `json_schema` type): the JSON contract is carried in the system prompt (a JSON-only output instruction is appended to it), the object is extracted from the plain completion with `extract_json_object` (tolerates code fences, thinking preambles, trailing prose), and the result is validated against the Pydantic model client-side with bounded retries (`max_attempts=2`, one corrective re-ask on malformed output). | 2026-09-22, amended 2026-09-24 (V3 P37/P49) | Some compatible endpoints reject `strict: true`; client-side Pydantic validation + retry covers correctness regardless. |
| 14 | Facts proposed via `/remember` stay in `proposed` status until the user taps the Confirm button; nothing is silently promoted, and only `confirmed` facts are ever fed into chat context. | 2026-09-22 | SPEC §14 requires explicit user confirmation for stored facts; the propose -> confirm/reject/supersede lifecycle keeps provenance auditable. |
| 15 | Contextual chat builds a selective, bounded context per turn (recent messages, today/upcoming items, pending reminders, recent workouts, confirmed facts, top-3 retrieved file chunks) rather than dumping the user's whole database into the prompt. | 2026-09-22 | SPEC §15 asks for context-aware answers; bounded sections keep prompt size predictable and cost low while covering the assistant's domains. |
| 16 | The worker process delivers reminders and daily digests itself through the Bot API using its own `aiogram` `Bot` instance (same token as the bot process); the bot process handles interactive traffic via polling. | 2026-09-22 | SPEC allows only bot/api/worker/postgres processes; the Bot API is callable from any process, so the worker can deliver durable sends without a message broker. |
| 17 | A digest whose configured time has already passed (worker was down, user just registered) is delivered immediately — due digests are late, not dropped. | 2026-09-22 | SPEC §16 requires daily digests without duplicates; "no spam" limits frequency (once/day per user), not timeliness. |
| 18 | Motivational messages are deterministic, state-derived templates (no AI call): at most one line, chosen from overdue / upcoming workout / streak / empty schedule, and suppressed when `motivation_enabled` is off. | 2026-09-22 | SPEC §17 asks for lightweight, non-spammy motivation derived from real state; templates are cheap, predictable, and testable. |
| 19 | E5 prefixes for `multilingual-e5-small` are applied centrally in `OpenAIEmbeddingProvider`: `embed_documents` prefixes `passage: ` and `embed_query` prefixes `query: `. Call sites pass raw text; chunk text and user queries are stored/returned without prefixes. | 2026-09-22 | multilingual-e5-small is a retrieval model that requires asymmetric prefixes; centralizing them avoids inconsistent application across ingestion and retrieval call sites. |
| 20 | Conversational mutations (calendar creates/cancels) are **bounded and typed**: the AI proposes a `PendingAction` row with a fixed `kind` from a closed registry (built-ins `create_item`, `cancel_item`), a JSON payload validated per kind, a human-readable summary, and a TTL (`expires_at`); nothing executes without an explicit user Confirm in the bot or Mini App. Expired/rejected actions are terminal. Fact replacement is a direct, always-visible confirm-then-propose flow (`supersede_fact`), not a model-proposed action. | 2026-09-23 | V2 requires conversational actions with confirm-before-write; a closed kind registry keeps the execution surface auditable and prevents the model from inventing arbitrary operations. |
| 21 | Proactivity is **deterministic and state-derived** (no AI calls): a weekly review nudge on the user's local Monday (once per ISO week) and a workout nudge when the last workout is older than 48 h (once per local day), each gated by per-user `ProactiveSettings` (enabled, quiet hours, max nudges/day, min interval). Delivery is deduped by a `NudgeDelivery` row keyed (user, kind, period) **committed before** sending — at-most-once: a failed send loses the nudge and is not retried (a nudge is a convenience, unlike the at-least-once reminders/digests). | 2026-09-23 | V2 asks for proactive nudges without spam; deterministic triggers + durable dedupe rows are cheap, testable, and survive worker restarts. |
| 22 | Hybrid retrieval has **no lexical prerequisite** (SPEC §17): the lexical tsvector arm (language-neutral `simple` config, ranked by `ts_rank`) and the vector arm (pgvector cosine) run **independently** and their ranked candidate sets are fused via RRF (K=60) with a minimum fused score dropping tail candidates; the result is empty only when both arms are empty, and an embedding outage degrades to lexical-only results. Citations are derived deterministically from the fused ranking. (Amended from a lexical-gated design: the gate silently dropped semantically-relevant chunks that shared no exact words with the query.) | 2026-09-23, amended 2026-09-24 | The lexical gate bounded cost (no embedding call for no-overlap queries) but at the cost of recall for paraphrased queries; making the arms independent recovers semantic matches while RRF keeps score-scale coupling between the arms decoupled. The embedding call is bounded by the model's decision to invoke the `documents` read tool. |
| 23 | The chat turn engine may propose memory automatically: salient facts extracted by the model are stored as `proposed` user facts (deduped against existing values) and enter the same confirm/reject/supersede lifecycle as `/remember` facts — never auto-confirmed, never fed back into chat context until confirmed. | 2026-09-23 | V2 requires durable memory without silent writes; reusing the fact lifecycle keeps provenance auditable and context bounded. |
| 24 | Optimistic stale-data protection is applied to the **pending-action path** (the AI-proposed mutation surface, where a preview→confirm gap lets data drift): item-mutation kinds (`update/complete/cancel/delete_item`) capture the target's `updated_at` at proposal time (the kind's `baseline`) and the executor raises `ActionStaleError` (→ action expired) if it drifted by execution time. Direct Mini App API mutations (`PATCH /items`, complete/cancel/delete) are immediate user-initiated writes with no proposal gap, so they are out of scope for this guard. | 2026-09-23 | The clobber risk only exists across a proposal→confirm delay; a `baseline` hook on the kind registry keeps the guard generic, and `updated_at` (already maintained via `onupdate=now()`) is the version token without a schema change. |
| 25 | Fact dedupe identity is the **`key_hash`** — the SHA-256 hexdigest of the normalized value (`" ".join(value.split()).lower()`) — not the truncated 255-char `key`, which can collide for long facts sharing a prefix. `key` is retained as a human-readable, display/debug-only field. The same normalized value maps to one hash, so re-proposing an identical fact is suppressed. **Rejection suppression is permanent, not time-bounded:** a `rejected` fact keeps its `key_hash` in the user's live set and blocks any automatic re-proposal of that exact value until the user deletes the row (deletion is the only way to clear the suppression; there is no TTL). A `superseded` fact does not block. When the model cites a `replaces_fact_id` (a confirmed-fact id from the `facts` tool), it is revalidated server-side (same user, status `proposed`/`confirmed`); an invalid reference is silently dropped and the proposal stored as a plain new fact. | 2026-09-24 | SPEC §16 requires collision-resistant dedupe and a documented stance on rejection-suppression duration; hashing the normalized value removes the prefix-collision class of bug, and making rejection suppression permanent (delete to clear) is the simplest, most predictable anti-spam behavior with no hidden expiry. |
| 26 | Meaningful-relevance filtering (SPEC §13, §17): the vector arm tracks each candidate's cosine distance separately and drops any candidate whose distance exceeds the configurable `retrieval_max_distance` bound (default 0.9; 0 = identical, 1 = orthogonal, 2 = opposite). Lexical (keyword-overlap) candidates are always kept regardless of the bound, so a semantically off-topic search never returns its nearest-but-unrelated chunks while keyword matches survive. The fused result exposes the chunk's best (minimum) vector distance, which adjacent-chunk merging preserves. | 2026-09-24 | A pure nearest-K vector recall returns its top-K even for an off-topic query, degrading answer quality; a configurable distance bound lets operators trade recall vs. precision per deployment, and keeping lexical candidates unbounded preserves keyword retrieval (and cross-language recall via the multilingual embedding) even when the semantic distance is large. |
| 27 | The lexical retrieval arm builds an **OR-style, operator-safe** tsquery (SPEC §13): the query is split into whitespace terms, each lowercased and stripped of every non-word character, then joined with `\|` so a chunk is recalled when it contains *any* of the query's words (not all, as `plainto_tsquery`'s implicit AND required). Ranking is `ts_rank` over the OR expression. A term-less query yields no lexical candidates. | 2026-09-24 | The prior AND gate dropped chunks that matched only a subset of the query's words (a common partial-overlap case) and treated user input as literal text; per-term normalization makes arbitrary user input incapable of being read as a tsquery operator (no injection, no raised errors), and OR matching restores keyword recall while RRF still balances it against the semantic arm. |
| 28 | Adjacent-chunk merging (SPEC §13) is **proximity-based and order-independent**: fused candidates are grouped by file and merged by position within a configurable `retrieval_merge_gap` bound (default 1 = strictly consecutive; a larger value bridges a small gap of un-retrieved chunks), with the merged span tracking its `position_end`, the maximum constituent score, and the minimum constituent vector distance; spans are then re-ordered by best score. Citations are **position-aware**: a file whose retrieved chunks span more than one position is annotated with its contiguous 1-based part range (``file.md (parts 2–3)``), while single-position sources are listed by name alone. | 2026-09-24 | The prior merge only joined a chunk to the span's *first* position and required the two chunks to be adjacent in the score-sorted list, so same-file chunks interleaved with higher-scoring chunks (or longer runs) were never merged; grouping by file and comparing against the span's *end* fixes both and is independent of fusion/score order. Position-aware citations let the user see exactly which part(s) of a file an answer drew from, at zero extra cost (positions are already indexed). |
| 29 | File ingestion is resource-bounded (SPEC §21): extracted text is capped at `MAX_EXTRACTED_TEXT_CHARS` (default 2 000 000), the per-file chunk count — and therefore the embedding batches and `file_chunks` rows — at `MAX_CHUNKS_PER_FILE` (default 2 000), and PDFs are rejected when they exceed `MAX_PDF_PAGES` (default 500) before any page is parsed. A file exceeding any cap fails **visibly** (`state=failed`, human-readable `error`, zero chunks written) rather than being silently truncated. DOCX extraction uses the **stdlib `zipfile`** streaming reader with a 64 MiB decompressed-XML cap (zip-bomb safe) and a regex over `<w:t>` runs; `python-docx` remains only as a test-fixture dependency for creating real DOCX files, never imported at runtime. Disk read, extraction, and chunking run via `asyncio.to_thread` so large files cannot starve the worker's event loop. The Mini App upload endpoint streams the body in 1 MiB reads, aborting with HTTP 413 the moment the size cap is exceeded, and removes any orphaned disk artifact if the database registration fails (`discard_storage`). Indexed files record `char_count` and `chunk_count` in `extra`. | 2026-09-24 | Hostile/compressed documents must not cause unbounded CPU/memory work in the single worker process; visible failure keeps the Files screen honest about what is actually searchable; stdlib streaming DOCX parsing removes a decompression-bomb vector and a runtime dependency; streamed upload reads bound memory for oversized bodies. |
| 30 | File lifecycle consistency on the single-server local volume (SPEC §11-12): deleting a file removes the disk artifact only **after** the database commit survives (the API route commits, then calls `discard_storage`), so a failed commit can never destroy the only copy of a local upload. Terminally failed ingestions are reaped by a bounded worker pass (`reap_terminal_artifacts`): a file whose state is `failed` AND whose job is in the terminal `failed` state AND that came from Telegram (re-downloadable) loses its disk artifact; local uploads keep theirs (disk is the only source, and `retry` needs it), and mid-backoff files (job still `pending`) are untouched. A local upload whose artifact has gone missing fails visibly ("Stored file data is missing and cannot be re-ingested") instead of erroring later with a confusing read failure. | 2026-09-24 | Without the commit-first ordering, a crash/commit failure between unlink and commit would leave a DB row with no recoverable bytes; without reaping, every permanently failed Telegram download would pin its (up to 20 MB) artifact on the shared volume forever; a missing-artifact check keeps the "only source" invariant visible in the Files screen. |
| 31 | Telegram output is **safe by default**: no `parse_mode` is set on either outbound bot (the bot process and the worker's notification bot), so every message is plain text. User content (filenames, titles, AI text) containing `<`, `>`, `&`, quotes, or HTML-like strings is always shown verbatim and can never be misrendered as markup or rejected by the Bot API for malformed HTML. All i18n strings are plain (no markup), so no output changes. | 2026-09-24 | The previous global `parse_mode=HTML` made any unescaped `<` in user content (a filename like `report <draft>.pdf`, a URL with `&`) a render-broken or API-rejected message; removing it makes the safe path the only path, eliminating the whole escape-discipline problem class (and any future call site inherits the guarantee). |
| 32 | Long Telegram output is bounded by one central splitter (V3 P24): `split_for_telegram` in `assistant/services/tg_text.py` cuts text into <=4096-char segments preferring `\n\n` paragraph breaks, then single `\n` line breaks (a boundary must be at least 1/3 into the window to avoid degenerate fragments), then a hard cut; segments are lossless (they concatenate to the original). `notifications.send_text` (worker: reminders, digests, nudges) and `answer_long` (bot: AI replies) route through it; an inline keyboard attaches to the *last* segment of a new-message stream, so it stays with the end of the content. | 2026-09-24 | A long model reply or digest above 4096 chars previously failed the whole send with a Bot API 400 and the user saw nothing; paragraph-preferred splitting keeps segments readable, losslessness keeps citations and tails intact, and centralizing the split means a new send site cannot regress to unbounded sends. |
| 33 | The bot is restricted to **private chats only** (V3 P25). The data model uses the Telegram *user* ID as the background-delivery chat ID (reminders, digests, nudges are all sent to the user's 1-on-1 conversation), so a task created in a group would deliver its notifications to the user's private chat — an incoherent experience. The main router therefore carries router-level filters (`F.chat.type == "private"` for messages, `F.message.chat.type == "private"` for callbacks) that keep every bot handler private-only, and a separate guard router — included in the dispatcher *before* the main router — answers non-private messages and callbacks with a localized `chat.private_only` explanation (messages as a normal reply, callbacks as an alert). The guard reads the sender's language from an **existing** user row only (no upsert), so a group interaction never creates a user, item, reminder, or FSM state. | 2026-09-24 | Restricting at the router level (rather than per-handler) guarantees a future handler cannot accidentally accept a group update; the guard-before-main ordering guarantees no bot logic ever runs for non-private chats; and the no-upsert language lookup keeps the rejection path side-effect free, matching the "no data from unsupported chats" stance. |
| 34 | The Mini App cancels in-flight renders by design (V3 P27): every `render()` carries a generation token and its own `AbortController`; superseded fetches are aborted and their DOM commits are guarded by an `isStale` check. In the Playwright console guard, a `net::ERR_ABORTED` `requestfailed` (and the matching `Failed to load resource ... ERR_ABORTED` console entry) is therefore a **controlled cancellation, not a failure**, and is ignored; real failures of completed requests (>=400 responses, non-abort request failures) are still reported. | 2026-09-24 | Without this, the correct cancellation behavior (dropping stale responses) would look like a broken request to the test harness and force a regression in the stale-render fix; the guard already trusted `204`-completed requests the same way, and aborts are equally trustworthy because the app issues them explicitly. |
| 35a | E2E specs share one deterministic test user (id 999999) for the whole run, so any spec that mutates durable user state (language, timezone, seeded items) must restore it in a `test.afterEach` hook — never only inline at the end of the test body, which is skipped on mid-test failure. Playwright spec order is filesystem order, not the order a developer assumes, so an un-restored setting silently reorders which specs break (V3 P30: `miniapp.e2e.ts` left `language: "en"` and every later Russian-string spec failed until a `test.afterEach` restore was added). Specs that seed calendar items must delete them in `afterEach` so strict-mode "single event cell" assertions in other specs keep holding. | 2026-09-24 | Test isolation for a shared user; prevents order-dependent E2E failures. |
| 35 | The Mini App speaks a **two-flavor time protocol** with the API (V3 P28): *instants* travel as ISO strings with an offset (the API returns/accepts aware UTC values), while *user-TZ wall-clock* values travel as **naive** `"YYYY-MM-DD[THH:MM]"` strings — the backend interprets naive datetimes in the user's configured timezone. Every date/time the app displays is computed in the user's IANA zone via `Intl.DateTimeFormat(..., {timeZone})` (`miniapp/js/time.js`), never in the browser's zone: calendar day keys, "today", the month's `[start, end)` fetch range (two-pass DST-safe midnight conversion; `monthStartUTC(y, m + 1)` is exactly the month's end), day grouping, and all displayed times. The datetime picker (flatpickr, which renders browser-local) is seeded from the instant's user-TZ wall clock so its `"Y-m-d H:i"` output is exactly the naive user-TZ wall value the backend expects. | 2026-09-24 | A user with a Moscow account on an Amsterdam device must see Moscow dates and times; browser-local `toLocale*`/`Date` arithmetic made "today", calendar event dots, listed times, and the fetched month range silently wrong across zones. Naive wall values on submit mean "what the user typed is what the user gets back" with no client-side conversion step. |
| 36 | Proactivity V3 (P38–P40): the Monday weekly review is a **deterministic summary** of the user's real state — overdue count, items completed since local-Monday-midnight, up to 3 upcoming high-priority titles within 7 days, and this week's workout count/minutes — with **no AI wording pass** (the optional AI pass is skipped: the deterministic text is already complete, and a model call per user per week adds cost/failure modes for no required behavior). An empty week sends nothing. A new **default-on** overdue nudge fires once per local day when any scheduled item's anchor (`due_at`, else `starts_at`) is past; it is user-toggleable. The workout nudge is **context-aware**: a scheduled `source="workout"` item at or after today's local start suppresses it (a plan on the books is the user's own answer); a slipped (past) plan does not. Concurrency: concurrent worker passes serialize on a `FOR UPDATE` lock of the settings row, and the delivery slot is claimed by `INSERT ... ON CONFLICT DO NOTHING` on (user, kind, period) — at-most-once across any number of sessions, no advisory locks. | 2026-09-24 | V3 asks for a meaningful weekly review plus an overdue nudge with bounded proactivity; deterministic composition keeps it testable, free, and spam-free, and the atomic reservation removes the check-then-insert race without a new lock primitive. |
| 37 | The 9B fast/no-think runtime (V3 P41): the turn-mode invariant — a non-blank `clarification` must not co-occur with any proposed `actions` (SPEC §8) — is enforced **in the Pydantic schema** (`AssistantTurn` after-validator), not in prompt prose; the bounded `chat_structured` repair loop (max 2 attempts) is the only recovery path, and an unrepairable contradiction raises `AIOutputValidationError` rather than executing half of a contradictory turn. Prompt action/tool docs are **registry-derived** (`_actions_doc` renders `kind(field:type?, ...)` from each payload schema with a compact type descriptor — enum value sets, `"YYYY-MM-DD HH:MM"` for datetimes, `T[]` for lists) and internal engine-filled fields are hidden via `Field(exclude=True)` (currently `expected_updated_at` on item-mutation payloads), so the docs stay compact for a small model and cannot drift from the schemas; no JSON schema is dumped into the prompt. | 2026-09-24 | Prompt-prose invariants are advisory and a 9B model will occasionally violate them; a schema-level invariant turns the violation into a typed validation error the existing repair loop already handles. Registry-derived, field-level docs replace a big JSON schema with a concrete, greppable catalog (types/enums/date format are the failure modes a small model actually hits), and `exclude=True` keeps internal drift-guard fields out of the model's view while the engine fills them. |
| 38 | Optional embedding degradation (V3 P42): chat credentials are the only **required** AI credentials — a deployment without an embedding provider runs **chat-only**. The composite provider reports `embedding_configured == False` and its embed methods raise `AIProviderError` (fast, no network). Consequences: (a) document uploads are rejected **at registration** (both Telegram and Mini App paths) with the visible `files.err_embedding_unconfigured` reason — no job is enqueued and (for local uploads) no disk bytes are written; (b) a `files.ingest` job enqueued **before** a config change to chat-only fast-fails with `FileUploadError` at the top of the pipeline (a file that can never be embedded must not spend its backoff budget retrying); (c) document search degrades to **lexical-only** — the vector arm is skipped by construction (logged as the expected mode, not an outage), lexical hits are returned as before, and the provider is never called. Chat, actions, facts, workouts, and every non-embedding feature are unaffected. | 2026-09-24 | §42 requires a deployment to boot and stay fully useful without an embedding provider; making chat the only required credential and gating every embedding touch point on a single `embedding_configured` property keeps the degradation explicit (visible upload rejection, visible pipeline fast-fail, reported lexical-only search) instead of a silent half-feature. |

| 40 | The Mini App test-auth bypass lives in a **test-only entry point, not the production app** (V3 P44). `Settings` has no test-auth fields at all (no `ASSISTANT_TEST_AUTH` flag, user id, or name), and the production `create_app()` (`assistant.api.main`) authenticates every request with a signed Telegram `initData` and never consults an environment flag for any bypass. | 41 | AI providers are **degradation components, not readiness gates** (V3 P45). `/readyz` returns 200 only when PostgreSQL is reachable (`SELECT 1`, 3-second timeout); `ai_chat` is `ok`/`degraded` on `settings.chat_api_key` and `ai_embedding` on `settings.embedding_configured`, and a `degraded` component never makes the service `not_ready`.
